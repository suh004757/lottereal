# 잠실살이 Phase 1 출시 체크리스트 (M5)

**공개 보류.** 이 문서는 `lottes.co.kr/jamsilsari/` POC 출시 절차다. 이 작업에서는 출시 스위치, 검색 노출, 링크, DB·Auth·메일 설정, 잡을 변경하지 않는다. 로컬 합성 테스트를 운영 권한, 배포, 모니터링 증거로 쓰지 않는다. 승인자·시각(KST)·대상 리비전·검증 결과는 개인정보 없이 상위 작업의 [STATUS.md](STATUS.md)에 기록한다.

## 승인과 실행 순서

- [ ] **H1 · 오너 / Legal Bot:** 브랜드 및 `by 롯데부동산`, 표시광고 필수 항목·책임, 확인 등급·중복·임차인 의뢰, 수수료, 수리 요청의 범위, 개인정보 고지·동의·보존을 검토한다. 계약 일정 규칙은 시행일·예외·공식 근거 링크를 확인한다. 거래완료 표시와 대리 접수의 저장·직접 의뢰 근거는 별도로 결론을 기록한다. 이번 Phase 1 공개 환경의 `SHOW_COMPLETED`는 OFF로 유지한다(목록·상세 직접 접근 포함). **H2** 이름은 잠실살이로 결정됐지만, 출시 승인 증거는 H1과 함께 남긴다. [SDD §11](SDD.md#11-사람-게이트-에이전트가-혼자-넘지-않는다)
- [ ] **공개 읽기 먼저 · 릴리즈 담당:** 후보 배포에서 비회원 목록·상세·필터를 검증한다(D0-8 1단계). H1/M5 공개 승인 전에는 noindex 유지, `public/Sitemap.xml`과 메인 링크 미변경. noindex는 접근 통제가 아니다. 일반 가입과 가입 버튼, 계약 화면은 OFF로 유지한다. 기존 고객·매물 데이터를 테스트로 넣지 않는다.
- [ ] **D0-8 2→3 → H3 · DB/Auth 오너:** 기존 admin·가족 업로더 역할을 먼저 확인한다. H6 승인 뒤에만 039를 적용하고 기존 업로더가 계속 업로드할 수 있는지 확인한다. 그다음 일반 테스트 계정의 비공개 데이터 및 사진 업로드가 모두 거부되는지 실증한다. 1→2→3이 끝난 뒤에만 H3에서 운영 신규 가입 설정과 UI를 연다. Redirect URL 목록에만 `https://lottes.co.kr/jamsilsari/*`를 추가하고 Site URL은 유지한다. Google provider·승인 도메인 및 매직링크 발송 제한을 확인한다.
- [ ] **H4/M4 · 오너 / QA:** 지정한 테스트 계정으로 임차인·임대인·무관 계정을 분리한다. 합성 계약으로 실제 매직링크(새 탭 포함), 최초 동의, 초대 수락·재발급과 이전 링크 무효, 무관 계정 차단, 수리 저장·상태 전파와 재등록의 관리자 큐 도달을 확인한다. 토큰·계약 데이터가 URL 전달, 로그, 분석 이벤트 또는 다른 계정 UI에 남지 않는지 확인한다. 브라우저 모의 응답은 DB/RLS 실증이 아니다. M4 검수 전 `ENABLE_CONTRACTS`는 OFF다.
- [ ] **기능별 보류 · 오너:** H6 전에는 037과 공유 매물 신규 게시, 메인 공개 범위 및 기존 문의 경로 변경을 차단한다. 실접수(`ENABLE_REQUESTS`)는 H1 및 해당 공개 DB 쓰기 승인·검증 뒤에만 연다(UI OFF만으로는 서버 쓰기가 막히지 않는다). H7 전 전용 메일·허용 발신자 미연동, H1 전 대리 접수 실수신·전환·연락 비활성. H0 승인 없이는 알림 없음. H8 없으면 지도 없이 진행. H5가 없을 때 비용·계약 등 입력 누락은 `미확인`; H5는 지표만 막는다.
- [ ] **출시 전 증거 · 릴리즈 담당 / 독립 검토자:** 후보 리비전의 Linux 테스트와 필수 CI, Gitleaks·패턴 검사, 배포 산출물의 비밀값/운영 자료 미포함을 확인한다. 격리 DB에서 역할·ACL/RLS, 적용/복구와 기존 버전의 새 스키마 호환을 증명한다. 기존 관리자 로그인·사진 업로드·매물·문의와 공개 목록·상세·sitemap 비회귀를 확인한다. 키보드·모바일·WCAG 2.2 AA 검사와 개인정보 네트워크 검토를 완료한다. 고객 문의 대응 창구, 기준선, 알림 수신자, 복구 담당자·전 버전을 지정한다.
- [ ] **M5 공개 · 오너 승인 후 릴리즈 담당:** 승인된 문구·고지·정책과 `brand.mjs` 표기를 반영한다. 공개 승인된 페이지에만 noindex를 해제하고 `public/Sitemap.xml`에 넣는다. 메인 매물 페이지 하단에만 “잠실살이에서 확인 상태와 함께 보기”를 추가한다. 메인 내비게이션 및 초대·계정·계약 화면의 검색 노출은 제외한다. H1/H2 STATUS 승인 기록, 실제 공개 URL 200, Linux에서 `python3 scripts/post_push_guard.py` 통과, 첫 실제 집계 보고서의 승인된 실행을 각각 기록한다. 이 문서 작업에서는 모두 미실행이다.

## 확인 시간과 복구 판단

릴리즈 담당과 복구 담당의 실명 대신 승인된 내부 역할/연락처를 운용 기록에 지정한다. 아래 창과 기준은 제안이며, 운영 기준값·대시보드·실행 권한·복구 절차가 확인되기 전에는 공개 보류다. 테스트용 신호와 실제 트래픽을 분리한다.

| 신호 | 확인 창·비교 기준 | 중단 조건과 담당 |
| --- | --- | --- |
| Pages 공개 URL/config, 기존 관리자·문의 및 승인 경로 | 배포 직전과 직후, 5분 내 재확인. 같은 합성 정상 흐름과 HTTP 상태 비교 | 공개/config 비정상 또는 필수 흐름 실패 시 확장 보류, 릴리즈 담당이 Linux 가드 및 AGENTS.md 복구 절차 적용 |
| Pages 및 활성 Auth/DB 경로의 오류율·p95 응답 시간·포화 징후(Origins/DB 연결 사용률, 이메일 발송 한도 등) | 배포 전 같은 길이의 30분 기준선과 첫 30분 관찰 구간; 낮은 트래픽은 합성 정상 경로와 별도 표기 | 운영 담당이 승인한 허용 범위 초과가 5분 창 2회 연속이면 확장 보류 후 복구 판단. 기준선·측정값 부재는 건강 확인 실패 |
| 개인정보·비밀값 노출, 무관 계정 접근, 기존 데이터·경로 회귀 | 단 한 건도 허용하지 않음, 전 검증 및 관찰 기간 | 즉시 중단. 오너/운영 담당이 노출 경로를 차단하고 기능을 닫은 뒤 이전 검증 버전으로 복구; 비밀값 노출은 로테이션 |

복구 시 공개 링크·sitemap과 noindex도 이전 상태로 확인한다. 프런트 복구가 Auth 설정·DB 쓰기 권한·기존 데이터까지 되돌리지는 않는다. DB/Auth 오너는 별도 승인된 차단·복구 절차를 사용하고, 데이터 삭제나 미검증 다운 마이그레이션을 자동 실행하지 않는다. 현재 배포·실측 기준선·복구 리허설은 미확인이다.

## 월간 집계 미리보기 (SDD §1.1, §8, M5)

`platform_metrics_report.py`는 JSON 한 건을 stdin으로 받아 Markdown을 stdout으로 내보낸다. DB·메일·분석 시스템에 연결하거나 파일을 쓰지 않는다. 예제는 합성 집계다.

```sh
printf '%s\n' '{"month":"2024-02","zigbang":{"receipt_days_observed":28},"platform":{"phone_clicks":5,"contracts":0}}' | python3 -B scripts/platform_metrics_report.py
python3 -B -m unittest discover -s tests -p test_platform_metrics_report.py
```

`month`는 `YYYY-MM`, 구간은 지난달 1일 00:00부터 이번 달 1일 00:00 직전까지 KST 기준이다. 업스트림에서 미완료 월·테스트 활동·중복 집계를 제외한다. `zigbang`, `platform` 안에는 아래 키의 비음수 정수 또는 `null`만 허용한다. 모르는 값은 생략하거나 `null`로 두고, 해당 월 전체를 확인한 0만 `0`으로 전달한다. 검증되지 않은 자료를 이어 붙이거나 공백을 0으로 채우지 않는다.

| 출처 | 입력과 집계 조건 |
| --- | --- |
| 플랫폼 행동 · 공급 | `phone_clicks`는 클릭, `listing_requests`와 `new_publications`는 각각 등록 요청·신규 게시. `site_visit`, `owner_listed`, `tenant_listed`는 월말 노출 매물의 확인 등급별 수. 임장 확인 비율은 3개 등급 모두 확인됐을 때 `site_visit` ÷ 등급 있는 매물 수. |
| 직방 receipts | `receipt_count`는 메일 알림 건수. `receipt_days_observed`는 수집 정상임을 별도로 확인한 날짜의 수(메일 존재 일수 아님). 월 전체 수집 확인이 없으면 건수는 `미확인`. 문의·고객·계약 분모로 사용하지 않는다. |
| 문의 | 양 채널 `calls`는 확인된 실제 통화 수, `inquiries`는 같은 정의로 직접 확인하고 중복 제거한 문의 합계. H6 전 플랫폼은 가족 확인 통화만 사용; H6 이후 `stored_forms`는 승인된 `inquiries.metadata.source_channel='platform'` 저장 폼만 집계. 리포터는 폼·통화·클릭·메일로 문의 합계를 추정하지 않는다. |
| 결과 · 비용 | `qualified_inquiries`, `visit_appointments`는 같은 정의의 검증된 수기 집계; 현 스키마에서 미지원이면 비운다. H5의 `contracts`, `ad_spend_krw`는 같은 달·채널의 `pf_channel_monthly` 승인 집계. 문의당 비용은 비용 ÷ `inquiries`, 계약당 비용은 비용 ÷ `contracts`; 분모 0이면 `—`, 분모 미확인 또는 양수 분모의 비용 미확인이면 `미확인`. 원 단위 반올림. |
| 운영 품질 (플랫폼) | `needs_recheck` ÷ `visible_listings`는 동일 월말 스냅샷. `close_lag_days`는 해당 월 종료 건의 완료~`closed_at` 반영 일수 합, `close_lag_observed`는 해당 건수. 관측이 불완전하면 비운다. |

`comparable_results`는 오너가 같은 월·비슷한 매물군·같은 결과 정의를 확인한 경우에만 `true`. 다르면 `false`, 알 수 없으면 생략한다. 채널 간 비교가 불가능해도 각 채널의 확인된 숫자는 남기며, 차이·합계·광고 축소 제안은 만들지 않는다.

오너와 릴리즈 담당이 첫 실제 실행 전에 월·출처·범위·수집 공백을 확인한다. 원문/자유 텍스트·고객/계정/매물 식별자·비밀값은 입력하지 않는다. 승인을 받은 월만 `docs/platform/metrics/YYYY-MM.md` 후보로 생성하고 소수 건 재식별 위험과 배포 제외를 확인한 후 기록한다. 오류 종료 시 기존 보고서는 유지한다. 같은 월·같은 집계는 같은 출력이며 재실행은 같은 월 파일을 검토 후 대체한다(누적 추가 금지). 매월 1일 KST 실행·커밋 및 잡 등록은 후속 승인 사항이며 여기서는 준비하지 않는다.
